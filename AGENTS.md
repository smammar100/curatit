# AGENTS.md — Curatit

## UI work: read this first

Before you create or change any UI, read **[DESIGN.md](./DESIGN.md)** (the design system's rules, layers and component picker) and the topic file in `docs/design/` for what you're touching. The live reference is `/system` (every token and component in both themes; sources in `src/components/system/sheets/`). `.cursor/skills/curatit-design/SKILL.md` points to the same files for Cursor.

- Build only from the system: atoms in `src/components/fundations/elements/`, molecules in `src/components/fundations/molecules/`, tokens in `src/styles/global.css`. Never hand-roll a button, field, menu, dialog, tabs, toast or card, and never copy a component's classes onto another element. Missing a piece? Add it to the system (component, sheet, docs: `docs/design/components.md`), then use it.
- Semantic colour tokens only (no `base-*`/`accent-*` in new code, no Tailwind palette, no hex, no `dark:` for colour or shadow). Words that carry meaning are at least `text-secondary-foreground`.
- Closed sets: use a component's variants and sizes as they are; `className` is for layout only (`cx` doesn't merge classes).
- Motion only from the tokens (`ease-out-quint`, `ease-in-out-quart`, `ease-in-quart`, the `animate-*` utilities), transform and opacity, nothing under reduced motion or on repeated keys.
- Check light and dark, 375px, keyboard and focus, then `npx tsc --noEmit -p .` and `npm test`.

**Curatit** is a **directory / showcase-style marketing site** built with Next.js on a Lexington Themes template: homepage highlights featured “sites” (with Fuse.js search), a magazine-style **blog**, a **digital product store**, and supporting pages (pricing, advertise, submit, sign-in/up, system styleguide). It fits **SaaS/marketing, template marketplaces, and curated listings**. Original template publisher: [Lexington Themes](https://lexingtonthemes.com/).

## Content collections (`src/lib/content.ts`)

`getCollection(name)` returns entries sorted by filename (so `10.md` sorts before `2.md`); `getEntry(name, id)` finds one. IDs are the filename without `.md`/`.mdx`. Frontmatter is validated with zod at build time and a bad file fails the build with the file name. Image fields are paths under `public/` (e.g. `/images/blog/1.jpg`) and must exist.

## Customization

The rules that keep the hero's critical path small: (1) every section below the hero is wrapped in `HydrateOnView` in `page.tsx`, which keeps its server HTML untouched while hydrating and renders it for real only once it scrolls into view (or focus lands in it), and gives it `content-visibility: auto` so the browser neither lays it out nor fetches its lazy images until it is near (the collage just below the fold was otherwise loading during the hero's paint and swinging mobile LCP by half a second); its observer's root is 1px short at the bottom (`rootMargin: "0px 0px -1px 0px"`), because the first section starts exactly at the fold and would otherwise count as intersecting from load with a ratio of 0, never cross a threshold, and never come alive: that broke the pinned problem → solution scroll until 2026-10-10). It starts watching only once the first paint is on screen (`afterFirstPaint()` in `src/lib/afterFirstPaint.ts`), and a section already in view by then waits for the visitor's first scroll, tap or key (noted from the moment the module loads, so the scroll that brings a section in counts; a page not at its top or opened on a `#hash` counts as moved): on phones the first section's heading shows under the hero at load while its stage is below the fold, and its code, render and covers used to land inside the measured window (2026-10-16); (2) the client components inside those sections are imported from `src/components/home/islands.tsx`, never directly, so their code, and all of framer-motion with its `MotionProvider`, downloads only when a section comes alive. A new client component on the homepage below the hero gets an `island()` export there; one used by the hero or navigation stays a normal import. The first section (`ProblemSolution`) is a plain `lazy()` there without the motion provider, since on a phone it is in view at load and `Scattered` animates its pop-in with CSS (`.scattered-in` in `global.css`), so framer-motion's animation features stay out of the page until a later section needs them (its intro hook still uses framer-motion's `useInView` and `useReducedMotion`). (3) The hero corridor is a server component and its covers request 256–640px files at quality 60, named in `data-src` / `data-srcset` and set once the page has loaded and its first contentful paint is on screen (`afterFirstPaint()`: `load` alone let the covers in ahead of a late first frame) by `global/DeferredImages`, a small client component beside them: on a served page its inline script does the swap (React keeps the server's script while hydrating and then drops it), and after a client-side navigation, where React never runs a script it creates, its effect does it; the footer's filmstrip and the sign-in wall's other covers load the same way, and the deferred `<img>`s carry `suppressHydrationWarning` because the swap can land before React hydrates them. Until the swap a deferred image is hidden (`img[data-src]` in `global.css`; Chrome otherwise draws an outlined box with a broken-image icon, which the owner flagged on the live homepage on 2026-10-17) and the tile's own fill shows (the corridor's cards: `bg-base-100` with an inset `ring-edge`); the swap marks it `data-fade` and it fades in over 400ms once loaded (at once under reduced motion). The browser's preload scanner starts every `src` it finds, lazy or not, within a few screens, so an image that must stay off the first paint has no `src` in the HTML. (4) Images inside client components render their `<Image>` only after mount (`useMounted()` in `src/lib/useMounted.ts`: `PostCover`, the `LibraryWindow` tiles, `BrandName`'s logo, the `Scattered` avatar, the MCP page's `SearchReel`; before mount a same-size empty box), so the demos' dozens of covers start after their section hydrates; every section after the first is `<HydrateOnView ahead>`, which comes alive half a screen before it scrolls in, so its covers are there by the time it does.
